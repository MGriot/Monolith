Chapter 2

Concepts

The handful of ideas that explain almost every behaviour in Monolith: one tree of tasks per project, statuses that roll up, roles that gate every request, and a schedule computed from estimates and dependencies.

One unit of work per operation

Compound changes (a task update that moves parent statuses and project dates, a project created from a template, an idea promoted to a task) commit once or not at all. Side effects that must not undo the change, such as queueing an e-mail, run in a savepoint.

Queues, not inline calls

Requests only insert rows into the e-mail and webhook outboxes. Workers deliver them after the commit with retries and backoff, using SKIP LOCKED so several processes never double-send.

In-process real time

The notification socket and the live whiteboard rooms keep their state in the backend process. That is why the image runs a single worker; scaling out needs a shared broker in front.

One permission layer

Every endpoint, the websockets and every MCP tool go through app/api/access.py. The UI hides controls by role, but the API is the gate.

Data model

Projects and the task tree

A project is the container: metadata, members and roles, custom fields, automations, files and sketches. Inside it, tasks nest to any depth; a task with children is a summary task, a task without is a work item. Each task gets a WBS code (2.3.1) from its position in the tree, recomputed whenever the tree changes.

Helios — Customer Data Platform Migration            project
├── 1 Discovery & design                             summary task
│   ├── 1.1 Inventory the 42 source systems          work item
│   └── 1.4 ◆ Gate 1 — architecture sign-off          milestone
└── 2 Platform foundation
    └── 2.2 Streaming ingestion: Debezium CDC        FS after 2.1

Trees load with one recursive query plus one query per relation, so depth and size do not multiply queries. "Subtasks" in older screens and the /subtasks API are the same task rows with a parent_id.

Roll-up

Status and progress roll-up

Statuses are Backlog, Todo, In Progress, On hold, Review and Done. Work items are set by people; summary tasks follow their children:

  • If any child is In Progress, the parent becomes In Progress.
  • If all children are Done, the parent tries to become Done, unless it is blocked by an unfinished predecessor, in which case it stays In Progress.
  • A task cannot be marked Done while a predecessor it depends on is not Done; circular dependencies are rejected (depth-first search).

The project's progress_percent weighs its top-level tasks:

100%Done
80%Review
50%In Progress
25%On hold
0%Todo, Backlog

A project's start and due dates follow its tasks: the earliest start and the latest planned due date (a task's hard deadline counts only when it has no due date). The project's own hard deadline is never changed by its tasks. Roll-up changes do not fire automation events (7.1).

Project roles

Every member of a project has one role. The owner and administrators (superusers) are always admin.

  • A task's owner or assignee can always read it and log time on it, even without a project role.
  • Roles are read from the database on every request, so changes take effect at once; removing a member removes access immediately, including open websockets on their next message.
  • Unknown role values are treated as viewer, and the database rejects them anyway.
  • MCP tokens act as their owner with exactly these roles (9.1).

Dependencies

A dependency links a predecessor to a successor in the same project, with a type and a lag in days (negative lag is a lead).

TypeThe successor…
FS finish-to-startstarts after the predecessor finishes (the default)
SS start-to-startstarts after the predecessor starts

SF start-to-finishfinishes after the predecessor starts

Critical path (CPM)

backend/app/core/cpm.py runs a forward and a backward pass over every task each time a project's task list is loaded:

  • Tasks without predecessors start at their planned start; others as early as their links allow, so gaps in the plan do not hide the longest chain. Completed tasks keep their actual span.
  • The backward pass is anchored at the computed finish, so the longest chain always has zero slack. A task's hard deadline can tighten it further and push slack negative, which means it is already late.
  • Summary tasks (tasks with subtasks and no links of their own) are not activities: they take their result from their children, critical when any child is, with the smallest child slack. Link a summary task directly and it becomes an activity again.
  • Each task gets is_critical and slack_days; the Gantt and task list highlight the chain, and get_critical_path returns it over MCP.

Classification

Topics, work types and tags

Topics (what it is about, with a colour) and work types (what kind of work) are managed lists. Global ones are defined by administrators; projects and tasks can add scoped ones that only exist there, and a project can whitelist which global entries it uses. Tags are free text and need no setup. Files in the File Hub can be tagged with topics too.
