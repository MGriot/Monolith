Chapter 1

Getting started

From an empty machine to a running Monolith with an administrator, in about ten minutes. Everything runs in containers; nothing but Podman or Docker is needed on the host.

You need rootless Podman with podman-compose ≥ 1.2, or Docker with Compose v2Ports one, 8080 by default
What runs

The stack

compose.yaml defines five services. Only the proxy is published to the host; everything else talks over two private networks.

ServiceContainerRoleReachable from
proxymonolith_proxynginx: serves the app, forwards /api (including websockets), /uploads and /mcphost, http://localhost:${HTTP_PORT:-8080}
frontendmonolith_frontendstatic React build on nginx-unprivilegedproxy
backendmonolith_backendFastAPI on uvicorn (non-root uid 10001), migrations at start-up, background workers, MCPproxy, mail network
dbmonolith_dbPostgreSQL 16 (pgdata volume)backend
mailservermonolith_maildocker-mailserver: internal SMTP for resets, verification, notifications and digestsbackend over mail_net
Production-like

Install and start

  1. Create the configuration. Copy the template and fill in at least the required values (next section). 
    cp .env.example .env
  2. Prepare the mail server once. It creates a self-signed TLS certificate and the sender mailbox; Dovecot stops the container two minutes after start if no mailbox exists. 
    scripts/mail-bootstrap.sh
  3. Build and start. 
    podman-compose up -d --build      # or: docker compose up -d --build
podman ps                          # every service should report (healthy)
  4. Open the app at http://localhost:8080. The interactive API documentation is at /api/docs.
Tip

The backend applies database migrations at start-up (AUTO_MIGRATE=true). Upgrading is git pull followed by the same up -d --build.

.env

Configuration

Every variable is documented in .env.example. These are the ones you set on day one.

VariableRequiredMeaning
POSTGRES_PASSWORDyesDatabase password (the database is never published).
SECRET_KEYyesSigns login and single-purpose tokens. Generate with openssl rand -hex 32; changing it signs everyone out.
FIRST_SUPERUSER_EMAIL, FIRST_SUPERUSER_PASSWORDfirst startThe first administrator, created at start-up if no account has that address. Remove the password afterwards.
MAIL_DOMAIN, SMTP_USER, SMTP_PASSWORDyesInternal mail server domain and the sender mailbox (for example noreply@monolith.local).
HTTP_PORTno (8080)Host port of the proxy.
APP_BASE_URLnoPublic origin used in e-mail links, the calendar feed and the MCP Host check.
ALLOW_SIGNUPno (false)Let people request an account on /register; an administrator approves each request.
MCP_ENABLEDno (true)Mount the MCP server at /mcp. Every client still needs a personal token (9.2).
MCP_ALLOWED_HOSTSnoExtra Host names accepted on /mcp besides APP_BASE_URL and localhost.
CORS_ORIGINSnoBrowser origins allowed to call the API cross-origin. The bundled proxy is same-origin and needs none.
EMAIL_ENABLED, SCHEDULER_ENABLEDno (true)Master switch for mail; weekly digest and daily deadline reminders.
RELAY_HOST …noRelay outgoing mail through a provider instead of delivering directly (8.6).
WEBHOOK_ALLOW_PRIVATEno (false)Allow webhooks to private addresses (self-hosted chat).
Careful

The API rejects special-use domains (.local, .test, .localhost, .invalid) in user addresses. MAIL_DOMAIN may be monolith.local, but accounts need a normal domain such as example.com.

Accounts

First sign-in

  1. Sign in with FIRST_SUPERUSER_EMAIL and its password. There are no default accounts; old addresses such as admin@admin.com do not work.
  2. Remove FIRST_SUPERUSER_PASSWORD from .env. It is only read when the account does not exist yet.
  3. Invite your team from Team Members: create accounts directly, or turn on ALLOW_SIGNUP and approve requests (8.1). People who get a temporary password must choose their own at first sign-in.
  4. Define global topics and work types in Metadata before the first projects (8.2).
  5. Create a project (3.1) and add members with a role (2.4).

Tests

# backend unit tests (no database); CI runs the explicit list in .github/workflows/ci.yml
cd backend && pip install -r requirements.txt pytest pytest-asyncio && python -m pytest -q tests/
# frontend
cd frontend && npm ci && npm run typecheck && npm test && npm run build
# live checks against a stack with a FRESH database (they create users and projects)
scripts/live-smoke.sh
# the generated parts of this guide
python scripts/docs/gen_reference.py --check
Danger

Never run scripts/live-smoke.sh against a stack that holds real data: it creates test accounts and projects. Use a throw-away stack with its own project name, port and volumes.

Rootless

Podman and rootless notes

  • All host ports are above 1024, so no net.ipv4.ip_unprivileged_port_start change is needed.
  • PERMIT_DOCKER=none on the mail server: rootless networking NATs source addresses and connected-networks could open a relay. The backend authenticates on port 587 with STARTTLS instead.
  • Mail state lives in named volumes; Postfix creates unix sockets that fail on Windows, macOS or network bind mounts. Only mailserver/config is bind-mounted.
  • loginctl enable-linger $USER keeps rootless containers running after logout on Linux.
  • Several stacks on one host need their own MAIL_CONFIG_DIR, project name and port; re-run scripts/mail-bootstrap.sh after rotating SMTP_PASSWORD.
  • The backend runs one worker: live whiteboard rooms and the notification socket are kept in process (2.1).
